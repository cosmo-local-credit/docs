# Arkitektura ng protocol network

Maaaring pag-ugnayin ng isang CPP-compatible deployment ang maraming Voucher at Pool sa pamamagitan ng opsyonal na registry, index, quote module, at pagtuklas ng ruta sa antas ng application. Nananatiling hiwalay na vault ang bawat Pool, na may sariling liquidity, may-ari, proxy administrator, configuration, at mga dependency.

Pinapatakbo ng Grassroots Economics Foundation ang pampublikong App sa [cosmolocal.credit](https://cosmolocal.credit). Maaaring gamitin ng ibang interface at deployment ang parehong pampublikong protocol. Ang pagpapatakbo sa App ay hindi awtomatikong ginagawang may-ari, tagapag-isyu, Tagapangasiwa, tumatanggap ng bayarin, o guarantor ang GEF para sa bawat contract sa ibaba.

Tingnan ang [Mga konsepto at bokabularyo](/fil/introduction/concepts) para sa pagkakaiba ng mga tungkuling may pananagutan at teknikal na kapangyarihan.

Ang magkaparehong Voucher sa iba’t ibang Pool ay maaaring lumikha ng **posibleng path sa graph**, hindi garantisadong ruta. Pinananatili ng production CLC Core ang reconciled graph mula sa impormasyon tungkol sa mga Pool, registry, catalog, balanse, bayarin, at on-chain event. Tinitiyak din nito ang kaugnay na holdings ng session Wallet. Hanggang tatlong palitan sa Pool ang hinahanap ng kasalukuyang pampublikong deployment.

Mabilis ang graph discovery ngunit tantiya lamang batay sa indexed block. Maaaring markahang stale ang resulta, at hindi pinatutunayan ng graph edge na makakadaan ang hinihinging halaga. Ginagamit ng filter na **Kredito** ang maaabot na set sa Pamilihan at kaugnay na discovery screen.

### May-awtoridad na quote

Pagkapili ng kalahok ng ruta at halaga, binabasa ng CLC Core ang bawat kaugnay na Pool sa iisang pinned block at inuulit ang suportadong `SwapPool` calculation. Inililista ng quote ang bawat hop, input at output, bayarin sa Pool, bayarin sa protocol, minimum na output, final recipient, at expiry. Limang minuto ang bisa ng kasalukuyang production quote.

Pagkatapos ay binubuo at sini-simulate ng service ang buong Calibur batch. Maaaring hindi ito makapagbigay ng quote dahil sa hindi suportadong token behavior o quoter, kulang na balanse sa Wallet, admission failure, token-balance cap ng Pool, kulang na liquidity, invalid fee domain, gas limit, o ibang dahilan ng revert.

Magkaibang ebidensiya ang discovery at quote. Ipinapakita ng discovery na maaaring may path; ang pinned-block quote ang may-awtoridad na panukala sa transaksyon. Maaari pa ring mag-expire o mawalan ng bisa ang quote kung magbabago ang kaugnay na state bago isumite.

### Pinirmahang atomikong batch

Sinusuri ng gumagamit ang **Mga detalye ng ruta** at pinipirmahan ang handang Wallet batch. Sa bawat hop, tinatawag ng batch ang `approve(pool, 0)`, `approve(pool, amountIn)`, at ang bounded overload ng `SwapPool.withdraw`. Ipinapatupad ng bawat bounded withdraw ang minimum na output at deadline. Bumabalik sa iisang Wallet ang intermediate Voucher bago gastusin ng susunod na Pool ang quoted amount; nananatili rin sa Wallet ang anumang bridging remainder.

Isinusumite ng relayer ang batch bilang isang same-chain na transaksyon na may `revertOnFailure = true`. Kung mabigo ang anumang approval o palitan sa Pool, sabay na babalik ang lahat ng route call—kabilang ang mga naunang hop at pagbabago sa allowance. Ito ang atomicity ng kasalukuyang same-chain transaction; hindi ito cross-chain atomicity, HTLC, escrow, netting, o awtomatikong Pool rebalancing.

Sinusuportahan ng kasalukuyang route flow ang mga EOA/Calibur Wallet na katugma sa App. Tinatanggihan ng kasalukuyang quote path ang Safe at ibang contract Wallet.

### Solidity `SwapRouter` at mga bayarin

Nananatiling quote-only ang Solidity `SwapRouter` ng Protocol v1.1.0. Maaari nitong tawagin ang quote function ng Pool sa isang ibinigay na path, ngunit hindi ito humahawak ng pondo, nag-aapprove ng token, o nagsasagawa ng palitan. Hiwalay na application-level coordinator ang production App/Core flow; direkta nitong tinatawag ang bawat `SwapPool` sa pamamagitan ng pinirmahang Wallet batch ng kalahok.

Ang mga bayarin sa Pool ay mananatiling nasa naaangkop na Pool para sa kalaunang pagkolekta. Ang anumang bayad sa protocol ay dagdag at direktang ililipat mula sa Pool na iyon sa naka-configure na tatanggap ng protocol nito sa panahon ng Palitan.

Walang hiwalay na route-service fee ang kasalukuyang App. Gayunman, maaaring may maraming bayarin sa Pool at protocol ang isang routed exchange dahil hiwalay na `SwapPool` settlement ang bawat hop.

### Receipt at failure status

Pinagsasama ng CLC Core ang ruta sa iisang tracking ID. Ipinapakita ng App ang **Nagpapalit**, **Napalitan**, o **Nabigo ang palitan**, kasama ang teknikal na status na **Nakabinbin**, **Kumpirmado**, o **Binalik**. Itinatala ng resibo ang transaction hash, route depth, bawat Pool at token pair, quoted at settled na halaga, bayarin sa Pool at protocol sa bawat hop, minimum na natanggap, at anumang intermediate remainder sa Wallet.

Ang isang ruta ay maaaring mabigo bago ang pag-sign dahil walang kwalipikadong landas o quote ay magagamit, sa panahon ng simulation dahil ang batch ay babalik, sa oras ng relay dahil ang naka-sign na transaksyon ay hindi maipadala, o on-chain dahil ang estado ay nagbago o isa pang kondisyon ng pagpapatupad ay nabigo. Ang isang nabigo o hindi magagamit na ruta ay hindi muling isusulat ang mga patakaran ng Pool, mag-discharge ng isang Voucher, o patunayan ang anumang bagay tungkol sa katuparan ng tagapag-isyu.

Opsyonal ang registry, limiter, quoter, fee policy, at protocol-fee controller. Kung walang registry, pumapasa ang anumang token sa admission check; kung walang limiter, walang cap ang deposit; kung walang quoter, raw-unit parity ang ginagamit ng Pool; at kung walang fee module, zero ang kaugnay na bayarin.

Ang limang sealable slot ay `feePolicy`, `feeAddress`, `quoter`, `tokenRegistry`, at `tokenLimiter`. Pinipigilan ng seal ang kasalukuyang may-ari ng Pool na palitan ang address na iyon sa pamamagitan ng setter nito, ngunit hindi nito pine-freeze ang internal state ng dependency. Hindi sakop ng limang seal bit ang address ng `protocolFeeController` at mode na `feesDecoupled`. Hiwalay din sa sealing ang kakayahan ng proxy administrator na i-upgrade ang Pool.

Maaaring i-withdraw ng may-ari ng contract ang available na liquidity ng Pool patungo sa napiling address. Sa decoupled-fee mode, hindi kasama sa landas na iyon ang naipong bayarin; nananatili ang kapangyarihang i-withdraw ang natitirang liquidity. Dapat suriin ng mga kalahok ang may-ari, proxy administrator, dependency controller, seal state, tumatanggap ng bayarin, at inilathalang patakaran ng Pool bago umasa sa isang Pool.

Para sa konseptuwal na disenyo sa likod ng mga contract na ito—kabilang ang curation, valuation, limitasyon, palitan, at pamamahala—tingnan ang [White Paper](/fil/white-paper).
