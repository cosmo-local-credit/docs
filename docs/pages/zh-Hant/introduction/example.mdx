# 代金券交換示例

這些示例說明代金券、需求、資金池、交換、履約和核銷之間如何相互關聯但彼此不同。它們用於說明相關角色，並不承諾某張代金券、某個資金池、某條路線或某種結果一定可用。

相關定義請參閱[概念與詞彙](/zh-Hant/introduction/concepts)。

## 簡單示例：一個資金池，三名參與者

一位農民提供食品籃，需要牙科服務。一位修理工提供車輛維修，需要食品。一位牙醫提供牙科服務，需要車輛維修。

每名參與者都建立一張條款清楚的代金券，並發布一個商品或服務項目：

- 農民的代金券可以用於食品籃；
- 修理工的代金券可以用於維修服務；以及
- 牙醫的代金券可以用於牙科服務。

牙醫建立一個名為 **Health Market** 的承諾資金池，公佈規則，准入三種代金券，並存入一些牙科服務代金券。資金池配置的代幣餘額上限決定它最多可以持有多少農民和修理工的代金券。App 中的這些 **“信用額度”** 是資金池容量控制，不是個人貸款。

農民看到牙醫對本地食品的需求，查看牙醫的代金券和資金池條款，然後用食品籃代金券換取牙科服務代金券。農民隨後預約、出示牙科服務代金券、接受承諾的治療，牙醫再記錄核銷。

修理工用維修服務代金券換取資金池中已有的食品籃代金券，並用它們獲得食品配送。牙醫可以用牙科服務代金券換取修理工的維修代金券，再用它們維修車輛。

每次資金池交換都會結算代金券餘額。每個發行方仍分別負責提供承諾的食品、維修或牙科服務。資金池使多方交換成為可能，不要求每一對參與者都在同一時間恰好需要對方提供的東西。

## 進階示例：路由交換

本例說明一張代金券如何從商品或服務項目和需求出發，透過兩個獨立治理的資金池完成交換。

### 1. 發行方公佈一項承諾

假設一家社區廚房建立數位餐食代金券。發行前，廚房公佈持有人作出知情決定所需的資訊：

- 廚房的身份和聯繫方式；
- 每張代金券所代表的餐食或其他商品或服務項目；
- 供應量、單位、標示價值以及廚房的履約能力；
- 可以在何處、什麼時間出示；
- 有效期、預約流程、費用、稅費或轉讓限制；以及
- 出示、履約、投訴、退款、替代和其他補救如何處理。

廚房是發行方，必須保持資訊準確，避免發行超過合理履約能力的數量，並按照持有人取得代金券時適用的條款履約承諾。建立代幣或發布商品或服務項目，不能證明廚房具備履約能力，也不會使 GEF 成為發行方。

廚房還發布一個描述可用餐食的 **商品或服務項目（Offering）**。代金券和該項目相關但不同：代金券是可兌換的承諾，而商品或服務項目幫助人們發現相關商品或服務。

### 2. 參與者發布需求

附近一所學校持有交通代金券，需要為一次活動準備餐食。學校發布一項 **需求（Want）**，說明餐食、數量、地點、時間和聯繫方法。

需求用於表達需要。它不會自動接受廚房的代金券、預留餐食、建立合同、授權交換或承諾學校一定繼續交易。學校仍需審查廚房、代金券條款、可用路線、報價和適用條件。

### 3. 獨立的資金池管理者篩選路線

兩個獨立治理的資金池連接這些資產：

1. 一個交通資金池准入學校的交通代金券和一種玉米代金券；以及
2. 一個食品保障資金池准入同一張玉米代金券和廚房的餐食代金券。

每個資金池管理者分別審查資產並公佈本資金池的規則，包括：

- 誰對資金池負責；
- 當前 `SwapPool` 所有者、代理管理員和重要依賴項控制者；
- 准入的代金券和其他受支援資產；
- 匯率或報價方法；
- App 中稱為 **“信用額度”** 的代幣餘額上限；
- 資金池費用和協議費用；
- 庫存和提取流動性的權限；以及
- 任何單獨出資的擔保、儲備或支援安排。

准入表示資金池配置的規則允許該代金券，但不能證明發行方具備履約能力、建立現金價值、形成保險，也不會把兩個資金池變成同一個治理實體。

### 4. 參與者提供庫存

交通資金池持有可用交通代金券交換的玉米代金券。食品保障資金池持有可用玉米代金券交換的餐食代金券。不同參與者可能按照不同的公佈安排提供這些庫存。

存款會增加可用的資金池庫存，但不會自動產生資金池份額、還款請求權、提款權、獎勵或治理權限。任何此類權利都必須來自另行披露的安排。

### 5. App 發現路線並提供報價

學校的錢包打開 **可存入（Credit）** 檢視並選擇餐食代金券。CLC Core 估算一條可能的路徑：

`transport voucher → mobility Pool → maize voucher → food-security Pool → meal voucher`（即：交通代金券 → 交通資金池 → 玉米代金券 → 食品保障資金池 → 餐食代金券）

這個發現結果還不是交換一定成功的承諾。每一跳都取決於當前准入、資金池代幣餘額上限、可用庫存、報價和費用配置、受支援的代幣行為以及服務資料是否及時。

學校選擇想要 **取得（Get）** 或 **花費（Spend）** 的數量。App 提供完整交換的報價。**路徑詳情（Route details）** 顯示兩次交換、數量和每一步的資金池費用及協議費用。學校繼續之前，會檢查最低收到數量和報價到期時間。

### 6. 持有人執行路由交換

學校選擇 **確認兌換（Confirm exchange）** 並授權完整路線。成功後，收據會顯示兩次資金池交換、交換數量和費用。

如果某一步失敗，兩次資金池交換會一起還原；第一次不會在沒有第二次的情況下保持結算。軟體如何構建和執行這筆交易，見[路由參考](https://software.cosmolocal.credit/contracts/routing)（英文）。

學校現在持有餐食代金券。鏈上交換屬於 **交換結算**，使學校取得餐食代金券條款所述的請求權；它不能證明廚房已經提供餐食。

### 7. 持有人出示代金券

在當前 App 中，選擇 **“兌付（Redeem）”** 會打開普通傳送流程，並預填代幣所有者的地址。把代金券發回去屬於向發行方出示，但本身不能證明廚房已經提供餐食。

學校按照廚房的預約或聯繫流程操作。廚房確認出示，並按照公佈條款提供承諾的餐食。

### 8. 發行方記錄履約和核銷

提供餐食後，廚房記錄已經履約的單位，使其不能被重復出示。根據公佈的流程，這可能包括接收、銷毀、取消或以其他方式停用退回的代金券。

如果廚房不履約承諾，持有人可以使用發行方公佈的投訴或補救流程，以及適用法律提供的任何權利。僅僅因為 App 找到路線或資金池支援交換，GEF 和兩個資金池管理者都不會因此成為兌換方。

**“申請停用（Request retirement）”** 是不同的操作：當前所有者請求管理員停用代金券。請求待處理期間，代金券仍保持活躍；請求可以獲批、被拒絕或被取消。獲批後，代金券會從活躍目錄中移除，但不會刪除合約、餘額、歷史或未履約的義務。這不是履約、核銷、銷毀或取消。

## 責任一覽

- **發行方：** 說明並履行代金券承諾，並記錄核銷。
- **發布需求的人：** 說明一項需要，但不會因此自動接受某張代金券或某條路線。
- **資金池管理者：** 分別公佈和管理各資金池的規則、匯率、費用、限額、控制權以及明確承擔的任何擔保。
- **持有人：** 審查發行方、代金券條款、資金池、路線報價、費用、錢包授權和適用法律。
- **CLC App 和 CLC Core：** 發現可能路線並報價，準備和 relay 已簽署批次，並對技術結算記錄分組；它們不能證明發行方已經履約。
- **技術控制者：** 只行使分配給自己的合約、依賴項、升級、目錄、路由服務或費用權限。
- **GEF：** 按照[服務條款](/zh-Hant/governance/terms)營運 CLC App 和支援基礎設施；它不會自動承擔上述其他角色。

## 路線不可用時

如果庫存不足、資金池上限會被超過、代金券未獲准入、代幣或 quoter 不受支援、錢包沒有足夠輸入、路線資料過時或最終批次模擬失敗，App 可能找不到路線，報價也可能失敗。隨著資金池狀態變化，報價還可能在提交前到期或失效。

這一結果不會改變需求、商品或服務項目，也不會改變發行方現有的代金券義務。參與者可以重新整理路線、選擇較小數量、使用另一張符合條件的輸入代金券，或等待資金池條件改變。

## 未來的信用安排

未來，某個資金池或其他責任方可以另行提供可償還墊款、擔保交易或其他信用產品。此類產品需要另行提供補充條款和交易條款，明確當事方、金額、到期日、費用或利息、擔保物處理、轉讓、違約、補救和核銷證據。

普通傳送、資金池存款、直接或路由資金池交換、代金券出示、履約或核銷，本身不會產生這些義務。
