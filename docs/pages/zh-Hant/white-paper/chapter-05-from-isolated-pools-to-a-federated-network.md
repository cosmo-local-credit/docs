# 5. 從孤立的資金池到聯合網路

當前 Protocol v1.1.0 支援透過一個 `SwapPool` 直接執行，並提供僅用於報價的 Solidity `SwapRouter`。生產環境中的 CLC App 和 CLC Core 透過準備一個已簽署的 Calibur 錢包批次，協調由參與者發起、經過最多三個資金池的同鏈路徑。合約本身不會執行多跳路徑；當前 App/Core 流程也不提供跨鏈 HTLC、託管路徑、自動資金池再平衡、批次淨額結算或跨網路清算。

本章說明當前的參與者路徑，並把它與需要新增資金池許可權的擬議協調方式區分開來。在兩種情況下，獨立資金池都保留自己的准入、估值、限制、費用、庫存、授權和治理規則。

## **5.1 分別衡量交換與履約**

路徑服務可以改善庫存獲取，但不會合並代金券和兌換生命週期。衡量時應把以下事件分開：

1. 路徑獲得報價；
2. 一次或多次資金池兌換在鏈上執行並結算；
3. 持有人向發行方出示代金券單位；
4. 發行方履行承諾；以及
5. 已履約單位被核銷。

報價或執行路徑的增加並不能證明履約增加。報告應說明附錄 C 要求的群組、期間、資產、估值方法和時間戳、排除項、糾正政策及鏈下證據。

**路徑示例：** 一所學校持有玉米代金券，但需要運輸代金券。CLC Core 可以識別相容的資金池庫存，在同一個固定區塊為選定路徑生成報價，併為學校錢包準備帶邊界的呼叫。只有每一跳都滿足報價邊界、限制、費用、庫存、受支援行為和政策，執行才會成功。最終兌換不能證明任何發行方後來履行了代金券承諾。

## **5.2 當前參與者路由和擬議的再平衡**

兩類活動需要不同的許可權。

**當前由參與者發起的執行。** CLC Core 根據輸入和輸出代金券及金額，從參與者符合條件的持倉中估算路徑。對於選定路徑，它在同一個固定區塊讀取資金池，生成權威報價，模擬完整批次，併為每一跳準備三次呼叫：重置 allowance、授予 allowance，以及帶邊界的 `SwapPool.withdraw`。參與者簽署後，中繼器提交一筆啟用 `revertOnFailure` 的同鏈 Calibur 交易。任何呼叫失敗，所有路徑呼叫都會回滾。應用把交易和逐跳結算彙總為一張收據。

每一跳都保留各自的責任資金池、報價輸入、授權、費用、限制、庫存和結算事件。當前應用不會另收路徑服務費。當前流程支援與應用相容的 EOA/Calibur 錢包，不支援 Safe 或其他合約錢包。

**選擇加入的資金池再平衡。** 資金池管理者可以公佈庫存目標、允許的交易對手、資產類別、報價偏差邊界和每期限制。可問責的服務可以搜尋相容的迴圈或鏈條，並且只執行已授權意圖。

再平衡必須由資金池選擇加入。資金池可以允許普通參與者使用路徑，而不授權服務移動庫存進行再平衡。未來授權可以僅允許特定資產、交易對手和金額。每次執行的跳轉都應產生收據，任何服務費應與資金池費用和協議費用分開披露。

跨鏈 HTLC 或託管執行也與當前同鏈原子批次不同。它需要已採納的超時、中止、控制方、恢復和剩餘風險規則。

### **5.2.1 聯邦和互操作性**

獨立部署可以執行自己的登錄檔、介面、路徑服務和政策配置，同時選擇相容的資料和收據標準。當前公開 App 使用其已配置的登錄檔和服務配置。跨配置執行仍取決於部署。

相容配置應：

- 確定其登錄檔根、服務運營方、控制者和適用條款；
- 披露允許和拒絕的對方,資產,介面卡和路線;
- 適用於每個參與池的授權,限制,費用和庫存約束;
- 儲存每次報價到收件證據;以及
- 允許其他功能的庫離開或選擇另一個登錄檔,而不刪除餘額或發行人義務.

相容性可以增加可用兌換路徑，並減少對單一登錄檔或運營方的依賴。它不會讓網路、CLC App、GEF 或其他資金池對某個發行方的履約負責。

## **5.3 擬議的網路費用分成與服務費模型**

當前 Protocol v1.1.0 對直接的組交換徵收了組費,並在配置時還徵收了一個額外的協議費.

生產環境中的路徑兌換會在每一跳獨立應用這些當前費用，並在報價和收據中逐項列出。它目前不會另收路徑服務費。

未來的專案可以單獨獲得:

1. 一個 **網路拉克** 定義為參與池收取的池費中的所述份額;以及
2. 一個 **路由費或服務費** 為了確定未來的服務.

擬議的網路拉克不是已經計算組費後,對全部交換金額的附加百分比.對於組 `p`:

τ_p = f_p · r_p

在哪裡 `f_p` 是池費率和 `r_p` 是該組費所分配給網路計劃的擬議份額.

在測量期間:

- **總池費** 是每個集團實際收取的集團費用的總額;
- **網路衝擊收據** 是這些收取的費用所宣告的份額;
- **服務費收據** 是單獨收取路由費或服務費;以及
- **專案費收據** 同等的網速收益加上服務費收益.

任何類別都不會被計數兩次.除非透過單獨的政策,否則將實際的協議費收益合法轉向未來計劃,目前的協議費不包括.

對於總體近似,讓:

- `Q_swap` 是對定義的佇列和期內執行的組交換值;以及
- `τ` 是擬議的網路拉克的有效率,以及對執行的交換價值進行了單獨確定的服務費.

然後:

F ≈ τ · Q_swap

每個輸入都需要一個明確的佇列,週期,單位,估值時間表,排斥和糾正政策.

### **5.3.1 符合現金條件的收入與實物收入**

任何交換或轉換都需要授權,可用庫存,披露場所,限制和實際執行.

讓 `χ` 是政策限制,轉換失敗和滑坡後現金資格的收費收益的實現份額.可使用現金的收益是:

F_cash ≈ χ · F

預算和破產平衡分析將使用實現的 `F_cash`,而不是總上市費用或物質庫存的表值.未來的計劃將單獨報告集團費用,網路收益,服務費,資產組成,轉換結果和可使用現金收益.

## **5.4 擬議的流動性計劃**

未來,單獨記錄的流動性計劃可能將資產分配給指定池或路由服務.當前的 `SwapPool` 合同不會列印池股,也不會自動建立償還,提款,獎勵,治理或利權.

任何程式都會發布:

- 負責實體和參與的資金池管理者;
- 貢獻的資產以及轉讓是否可償還,可撤銷,捐贈或授予;
- 監護和技術控制安排;
- 允許使用,限制,鎖定,退出門和損失分配;
- 費用或激勵金的資格,以及該金額是否可能為零;
- 報告,衝突,投訴和補救措施;以及
- 轉移,終止和處理剩餘資產和義務.

實質性風險包括難以交換或履行的庫存,現金資格較低,發行方未能執行,合同或供應商失敗,治理變化和退出限制.限制,儲備,收據和儀表板可能會減少或揭示一些風險;它們不會消除損失.

對於後期分析指標,讓:

- `ϕ` 是根據該計劃透過的條款分配的專案費收益的實現部分;以及
- `K` 是該計劃所涵蓋的資產在一個指定的方法下衡量的價值.

然後:

FeeFlow_LP ≈ (ϕ · F) / K = (ϕ · τ · Q_swap) / K

該指標描述了每項測量專案資產的履約費用流動.它不是APY,預測,股息或保證收益.報告將保持交換量,贖回表現,發行人履行,清算,持有時間,損失,提款和費用收據分開.
