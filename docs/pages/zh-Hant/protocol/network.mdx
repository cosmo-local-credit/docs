# 協議網路架構

相容 CPP 的部署可以透過可選的登錄檔、索引、報價模組和應用層路徑發現功能，連線多個代金券與資金池。每個資金池仍是獨立的保管庫，擁有自己的流動性、所有者、代理管理員、配置和依賴項。

Grassroots Economics Foundation 在 [cosmolocal.credit](https://cosmolocal.credit) 運營公開的 CLC App。其他介面和部署也可以使用同一套公開協議。運營該應用並不會自動使 GEF 成為下圖每份合約的所有者、發行方、資金池管理者、費用接收方或擔保人。

有關責任角色與技術許可權之間的區別，請參閱 [概念和術語](/zh-Hant/introduction/concepts)。

共享代金券會形成一條**可能的圖路徑**，而不是有保證的路徑。生產環境中的 CLC Core 根據資金池、登錄檔、目錄、餘額、費用和鏈上事件資訊維護經過對賬的圖，並核實會話錢包中的相關持倉。當前公開部署最多搜尋包含三次資金池兌換的路徑。

圖發現速度快，但只是截至已索引區塊的估算。結果可能被標記為過時，圖上的連線也不能證明所需金額可以透過。應用的**可存入**篩選器會在市場和相關發現頁面使用這組可到達的代金券。

### 權威報價

參與者選擇路徑和金額後，CLC Core 會在同一個固定區塊讀取每個相關資金池，並重現受支援的 `SwapPool` 計算。報價會列出每一跳、輸入和輸出、資金池費用、協議費用、最低輸出、最終接收方和到期時間。當前生產報價的有效期為五分鐘。

服務隨後構建並模擬完整的 Calibur 批次。不受支援的代幣行為、不受支援的報價器、錢包餘額不足、准入失敗、資金池代幣餘額上限、流動性不足、無效費用域、Gas 限制和其他回滾，都可能使系統無法提供報價。

路徑發現和報價是不同的證據。發現表示路徑可能存在；固定區塊報價才是權威的交易提議。即使如此，若相關狀態在提交前變化，該提議也可能過期或失效。

### 已簽署的原子批次

使用者核對**路徑詳情**並簽署準備好的錢包批次。每一跳都會呼叫 `approve(pool, 0)`、`approve(pool, amountIn)` 和有限額的 `SwapPool.withdraw` 過載。每次限額提取都會執行最低輸出和截止時間。下一個資金池花費報價金額前，中間代金券會回到同一個錢包；任何橋接餘量都留在該錢包中。

中繼器把批次作為同一條鏈上的一筆交易提交，並將 `revertOnFailure` 設為 `true`。如果任何授權或資金池兌換失敗，所有路徑呼叫——包括此前各跳及其 allowance 變化——都會一起回滾。這是當前同鏈交易的原子性；並不等於跨鏈原子性、HTLC、託管、淨額結算或自動資金池再平衡。

當前路徑流程支援與應用相容的 EOA/Calibur 錢包。當前報價路徑會拒絕 Safe 或其他合約錢包。

### Solidity `SwapRouter` 與費用

Protocol v1.1.0 的 Solidity `SwapRouter` 仍然僅用於報價。它可以沿給定路徑呼叫資金池報價函式，但不會持有資金、授權代幣或執行兌換。上述生產 App/Core 流程是單獨的應用層協調器，它透過參與者已簽署的錢包批次直接呼叫每個 `SwapPool`。

資金池費用保留在相關資金池中，供之後收取。協議費用是額外費用，並在兌換過程中由該資金池直接轉給已配置的協議接收方。

當前應用不會另收路徑服務費。不過，一次路徑兌換仍可能包含多筆資金池費用和協議費用，因為每一跳都是一次獨立的 `SwapPool` 結算。

### 收據與失敗狀態

CLC Core 用一個跟蹤 ID 彙總路徑。應用顯示**正在兌換**、**已兌換**或**兌換失敗**，並顯示**待處理**、**已確認**或**已回滾**的技術狀態。收據記錄交易雜湊、路徑深度、每個資金池和代幣對、報價金額和已結算金額、逐跳資金池費用和協議費用、最低收到金額，以及錢包中留下的任何中間餘量。

路徑可能在簽署前失敗，因為沒有符合條件的路徑或報價；可能在模擬時失敗，因為批次會回滾；可能在中繼時失敗，因為已簽署交易無法提交；也可能在鏈上失敗，因為狀態變化或其他執行條件不滿足。失敗或不可用的路徑不會改寫資金池規則、核銷代金券，也不能證明發行方是否履約。

登錄檔、限制器、報價器、費用政策和協議費控制器都是可選的。未配置登錄檔時，任何代幣都能透過准入檢查；未配置限制器時，存入不設上限；未配置報價器時，資金池按原始單位的一比一關係處理；未配置費用模組時，相應費用為零。

五個可封存槽位是 `feePolicy`、`feeAddress`、`quoter`、`tokenRegistry` 和 `tokenLimiter`。封存會阻止當前資金池所有者透過設定函式替換該地址，但不會凍結依賴合約的內部狀態。`protocolFeeController` 地址和 `feesDecoupled` 模式不受這五個封存位控制。代理管理員升級資金池實現的許可權也獨立於封存機制。

合約所有者可以把可用的資金池流動性提取到其選擇的地址。在費用解耦模式下，已累積費用會從該提取路徑中預留；所有者仍可提取其餘流動性。參與者在依賴某個資金池前，應檢查其所有者、代理管理員、依賴項控制者、封存狀態、費用接收方以及公佈的資金池規則。

有關這些合約背後的概念設計，包括篩選、估值、限制、交換和治理，請參閱 [白皮書](/zh-Hant/white-paper)。
