# Protocol network architecture

A CPP-compatible deployment can connect many Vouchers and Pools through optional registries, indexes, quote modules, and application-level route discovery. Each Pool remains a separate vault with its own liquidity, owner, proxy administrator, configuration, and dependencies.

Grassroots Economics Foundation operates the public App at [cosmolocal.credit](https://cosmolocal.credit). Other interfaces and deployments can use the same public protocol. Operating the App does not automatically make GEF the owner, issuer, Steward, fee recipient, or guarantor for every contract shown below.

See [Concepts and vocabulary](/introduction/concepts) for the separation between accountable roles and technical powers.

A shared voucher creates a **possible graph path**, not a guaranteed route. The production CLC Core service maintains a reconciled graph from Pool, registry, catalog, balance, fee, and chain-event information. It also verifies the session wallet's relevant holdings. The public deployment currently searches paths of up to three Pool swaps.

Graph discovery is fast but estimated as of its indexed block. A result may be marked stale, and a connection does not prove that the desired amount can pass through it. The App's **Credit** filter uses this reachable set for the Market and related discovery screens.

### Authoritative quote

After a participant selects a route and amount, CLC Core reads every relevant Pool at one pinned block and reproduces the supported `SwapPool` arithmetic. The quote identifies every hop, input and output, Pool fee, protocol fee, minimum output, final recipient, and expiry. The current production quote deadline is five minutes.

The service then constructs and simulates the complete Calibur batch. Unsupported token behavior, unsupported quoters, insufficient wallet balance, admission failures, Pool token-balance caps, insufficient liquidity, invalid fee domains, gas limits, and other reverts can prevent a quote from being offered.

Discovery and quoting are different evidence. Discovery says that a path may exist; the pinned-block quote is the authoritative transaction proposal. Even that proposal can expire or become invalid if relevant state changes before it is submitted.

### Signed atomic batch

The user reviews **Route details** and signs the prepared wallet batch. For every hop, the batch calls `approve(pool, 0)`, `approve(pool, amountIn)`, and the bounded `SwapPool.withdraw` overload. Each bounded withdrawal enforces a minimum output and deadline. Intermediate vouchers return to the same wallet before the next Pool spends the quoted amount; any bridge remainder stays in that wallet.

The relayer submits the batch as one transaction on the same chain with `revertOnFailure` set to `true`. If any approval or Pool swap fails, all route calls—including earlier hops and their allowance changes—revert together. This is current same-chain transaction atomicity. It is not cross-chain atomicity, an HTLC, escrow, netting, or automatic Pool rebalancing.

The current route flow supports the App's compatible EOA/Calibur wallets. A Safe or another contract wallet is rejected by the current quote path.

### Solidity `SwapRouter` and fees

The Protocol v1.1.0 Solidity `SwapRouter` remains quote-only. It can call Pool quote functions across a supplied path, but it does not hold funds, approve tokens, or execute swaps. The production App/Core workflow described above is a separate application-level coordinator that calls each `SwapPool` directly through the participant's signed wallet batch.

Pool fees remain with the relevant Pool for later collection. Any protocol fee is additional and is transferred directly from that Pool to its configured protocol recipient during the swap.

The current App adds no separate routing-service fee. A routed exchange can nevertheless contain several Pool fees and protocol fees because every hop is a separate `SwapPool` settlement.

### Receipt and failure states

CLC Core groups the route under one tracking ID. The App shows **Exchanging**, **Exchanged**, or **Exchange failed**, with a technical status of **Pending**, **Confirmed**, or **Reverted**. The receipt records the transaction hash, route depth, each Pool and token pair, quoted and settled amounts, per-hop Pool and protocol fees, minimum received, and any intermediate remainder left in the wallet.

A route can fail before signing because no eligible path or quote is available, during simulation because the batch would revert, during relay because the signed transaction cannot be submitted, or on-chain because state changed or another execution condition failed. A failed or unavailable route does not rewrite a Pool's rules, discharge a voucher, or prove anything about issuer fulfillment.

The registry, limiter, quoter, fee policy, and protocol-fee controller are optional. With no registry, any token passes the admission check; with no limiter, deposits are uncapped; with no quoter, the Pool uses raw-unit parity; and with no fee modules, the corresponding fees are zero.

The five sealable slots are `feePolicy`, `feeAddress`, `quoter`, `tokenRegistry`, and `tokenLimiter`. A seal prevents the current Pool owner from replacing that address through its setter, but it does not freeze the dependency's internal state. The `protocolFeeController` address and `feesDecoupled` mode are not covered by those five seal bits. The proxy administrator's ability to upgrade the Pool is also separate from sealing.

The contract owner can withdraw available Pool liquidity to a chosen address. In decoupled-fee mode, accrued fees are reserved from that path; the power to withdraw the remaining liquidity still exists. Participants should inspect the owner, proxy administrator, dependency controllers, seal state, fee recipients, and published Pool rules before relying on a Pool.
